Gantt Timeline for Jira Dashboard

Last updated: 3 October 2026

This page covers everything the app does. It is written to match the app's behaviour, including the parts that are unflattering — where the numbers can mislead, this page says so.

1. What the app does

It is a Jira dashboard gadget that draws a read-only Gantt timeline. You give it a JQL filter. Each matching work item becomes one horizontal bar on a shared date axis, with its key and summary on the left. The app does not write anything back to Jira: no dragging, no dependency lines, no rescheduling.

What it draws:
  • a bar per work item, from its start date to its end date
  • progress inside the bar, from time spent against the original estimate where both are set, and fully filled when the item is done
  • swimlanes, if you group rows by a field — Epic, version, assignee, team, or any other field your instance has
  • a dashed "today" line, so that "overdue" is readable as a distance and not just a colour
  • an overdue marker on bars whose end date has passed while the item is still open

2. Requirements

  • Jira Cloud.
  • A dashboard you can edit.
  • A JQL filter, and a decision about which of your fields hold the start and end dates.

3. Add the gadget to a dashboard

  1. Open a Jira dashboard and choose Edit.
  2. Choose Add gadget and search for Gantt Timeline.
  3. Add it, then open its configuration (the gadget's menu → Configure).
  4. Fill in the four settings below and choose Save.

4. Settings

JQL filter

Which issues appear on the timeline. Unlike an "in progress" chart, this one includes finished items as well — the point of a Gantt view is the gap between planned and actual dates, and completed work is half of that comparison.

If you paste a filter that already ends with ORDER BY (which is what Jira's own issue search gives you), that is accepted: the app strips it and applies its own ordering. It does this so that truncation behaves predictably — see section 7.

Start date field and End date field

The two fields the bars are drawn from. There is no single correct answer — it depends on your instance. Jira Software has a built-in Start date, some organisations add their own Target start / Target end fields, and many teams simply use Due date as the end. The gadget lists the date fields your instance actually has and saves your choice by field ID, so renaming a field or switching Jira's display language does not break an existing gadget.

Fall back to the creation date when the start date is empty

On by default. When an item has no start date, its creation date is used instead so the bar can still be drawn — but those bars are drawn dashed and the count is shown under the chart, because a borrowed date is not the same thing as a planned one. Turn it off and those items are excluded and counted instead.

Group rows by

Optional. Groups the rows into swimlanes by any field. Swimlanes are ordered by the earliest start date in them, and rows whose grouping field is empty go into a lane of their own at the bottom.

5. Where the dates come from, and where they don't

The app never guesses a date silently. Every row is either drawn from the field you picked, or from a fallback that is marked on the chart, or excluded and counted under the chart.
SituationWhat the app does
Start date is setThe bar starts there
Start date is empty, fallback onThe bar starts at the creation date and is drawn dashed
Start date is empty, fallback offThe row is excluded and counted as no start date
End date is setThe bar ends there
End date is empty and the item is finishedThe bar ends at the resolution date and is drawn dashed
End date is empty and the item is unfinishedThe row is excluded and counted as no end date. An open item's end date is not invented
End is before startThe row is still drawn, and the two fields disagreeing is called out in the row's tooltip rather than silently swapped

An item counts as finished if either its status category is Done or it has a resolution date. Both are checked because custom workflows do not always set both.

6. What "progress" means

When time spent and an original estimate are both filled in, the filled portion of the bar is their ratio. When the item is done, the bar is filled completely. When neither value is set, the bar shows no progress at all — the app does not invent a percentage from a status name, because two teams' "In Progress" mean different things and a fabricated number is worse than an absent one.

7. Two limits, and why they are stated on screen

  • 60 rows are drawn. Rows are taken in start-date order, so the timeline reads left to right; the chart says how many were not drawn.
  • The query stops after a fixed number of pages (2,000 issues). Because the query is ordered by creation date before that cut, the items dropped are the newest, not the oldest. When it happens, the chart says so.

Both are reported on screen. A silent cap would make a partial timeline look like a complete one, which is the failure mode this app is most careful about.

8. Languages

The gadget interface is available in English and Chinese (Simplified). Field names are shown as your Jira displays them, with the English name added in brackets when it differs — several fields in one instance often have similar localised names.

9. Data and privacy

The app reads issues through the Jira REST API using a read-only scope. It does not send data to any external service, and it has no third-party integrations. The full description of what is read, what is stored and where is in the privacy policy.
